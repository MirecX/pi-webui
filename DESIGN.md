# pi-webui — Design

A web UI that mirrors a running pi coding-agent session in the browser and lets you
interact with it (compose, steer, interrupt, switch model/thinking, fork/resume,
answer HITL dialogs) — **without touching SSH or a terminal**.

This document is the reference for the build. It was produced by stress-testing the
idea and is updated in place as decisions crystallise.

## 1. Positioning

- **Controller, not client**: pi-webui drives its own headless `pi --mode rpc`
  instances. It does **not** attach to a live interactive TUI session (a TUI-owned
  process has no external control channel, and dual-controlling one agent is a mess).
- "Mirror TUI content" = render the *same content* (messages, thinking, tool calls,
  bash output) as web-native markup — **not** a terminal emulator. The live
  interactive-command-terminal handoff is deliberately **out of scope for V1** (see §5).

## 2. Stack

| Layer | Choice |
|-------|--------|
| Server | **C# / ASP.NET Core** (REST + WebSocket, static file hosting) |
| Frontend | **TypeScript + a light reactive layer** (no heavy framework) |
| Agent protocol | pi **`--mode rpc`** JSONL over stdin/stdout (versioned, stable) |
| Session storage | pi's own JSONL session files (`~/.pi/agent/sessions/...`) |

## 3. Runtime model

- **One server process** (detached from any SSH session — started at container boot
  or launched on demand) **spawns and owns N dedicated `pi --mode rpc` child
  processes** — one per session — each with `cwd=/workspace`, running as `yolo`.
- The server talks JSONL framing to each child's stdin/stdout and multiplexes the
  event streams out to browser tabs over WebSocket.
- The server is the only writer to each child's stdio — it is the single controller.

```
[browser]
   │  HTTP/WS (token auth)
   ▼
[pi-webui server (C#), detached, yolo user]
   │  spawn + stdio (JSONL RPC)
   ▼
[pi --mode rpc child #N, cwd=/workspace]  ← one per session
```

## 4. Session model

- **On-demand, user-initiated lifecycle.** A session is created only when the user
  *initialises* it — never implicitly on tab/connect.
- Concurrent **named sessions** (each its own `pi --mode rpc` child). A browser tab
  attaches to one session's stream at a time.
- Three lifecycle actions (distinct):
  - **`init`** — create a new session (or resume an existing stored one).
  - **`recycle`** — kill the child process but **preserve the history file** (the
    session stays resumable/forkable). A separate action frees process only.
  - **`delete`** — remove the session file permanently.
- **Auto-title:** on the first user message of an unnamed session, the server fires a
  tiny, non-blocking, no-tools completion at the box's default model endpoint to
  generate a short title (e.g. `"Yo!"` → `"Casual greeting"`). Fallback while
  pending / on failure: truncated first message + timestamp. Never blocks the agent
  turn.

## 5. Feature set (V1)

Full pi-RPC surface, **minus TUI-exclusive features**:

**In scope**
- Compose / send (`prompt`), steer (`steer`), follow-up (`follow_up`), abort
  (`abort`)
- Live mirror: streaming assistant messages, thinking, tool calls, bash output
  (`message_update`, `tool_execution_*`, `bash_execution_update`, `agent_*`, `turn_*`)
- Model selection + thinking-level switch (`set_model`/`cycle_model`,
  `set_thinking_level`/`cycle_thinking_level`, available lists)
- Session management: `fork`, `clone`, `switch_session`, `new_session`, session
  browser, `get_tree`/`get_entries`/`get_messages`
- Compaction + auto-retry controls
- HITL dialogs: pi's `select`/`confirm`/`input`/`editor`/`notify` requests surfaced
  as browser modals (grilling, `/ask`, confirm-yes/no resolve in the webui)
- State: `get_state`, `get_session_stats`, `export_html`

**Out of scope (V1, TUI-exclusive)**
- `app.suspend` / job control (meaningless headless — use `recycle`)
- **Live interactive-command-terminal handoff** (typing into a running interactive
  process) — would need an embedded xterm.js + PTY bridge; deferred to V2
- True-term input semantics (IME hardware cursor, image-as-ANSI-art) — N/A on web

## 6. Auth & network

- **Token auth** for all HTTP + WebSocket requests.
- Token stored in a **config file**, container-agnostic:
  `~/.pi/agent/extensions/pi-webui/config.json`
  ```json
  { "token": "<auto-generated-on-first-run>", "port": 8456 }
  ```
- Token is auto-generated on first run and printed once; rotation = edit the file.
- **Ports:** internal `8456`; external mapping = `HOST_PORT + 10000`
  (e.g. SSH `22223` → web `32223`), **opt-in** in compose.
- Security posture: the web session can run arbitrary commands in `/workspace` —
  treat it like a root shell on the box. README carries the same credential warnings
  as yolobox.

## 7. Container readiness (yolobox)

The public yolobox image is **not** forced to include pi-webui. It is made *ready*:

- `docker-compose.yml` exposes an **optional** port mapping `"${HOST_PORT:-22222} + 10000":8456` (disabled by default).
- No entrypoint changes and no build-time install. pi-webui is installed **on
  demand** into the container exactly like pi-subagents (clone its own repo into
  `~/.pi/agent/extensions/pi-webui/` at runtime).

## 8. Packaging

- Own repo: `MirecX/pi-webui` (default branch `master`).
- Installed on demand into a container:
  ```bash
  git clone https://github.com/MirecX/pi-webui ~/.pi/agent/extensions/pi-webui
  cd ~/.pi/agent/extensions/pi-webui
  # build backend + frontend, then run the server (systemd/nohup/tmux or a launcher)
  ```
- Config written to the extension's `config.json` on first launch; token printed.

## 9. Open items (non-blocking, locked where noted)

- Frontend reactive layer: a small TS module for bindings/streaming (no framework) — **locked**.
- Config path/schema — **locked** (§6).
- Port scheme — **locked** (§6).
- (Deferred) V2: embedded xterm.js live-terminal handoff, per-session provider picker
  if the box exposes more than one model set.
